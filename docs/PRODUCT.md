# What is Emprint?
Emprint is a personal publishing and archive platform
designed for people to leave traces of their thoughts,
works, memories, and creative journey on the web.
It is not only a blog generator or portfolio builder.
Emprint exists to help people create a personal space
that reflects who they are,
how they think,
and how they have evolved over time.
The platform values:
- process over outcomes
- personal traces over polished branding
- curation over endless accumulation
- permanence over virality
- quiet self-expression over algorithmic attention
Emprint should feel like:
- a personal room
- a shelf of selected works
- a printed archive
- a long-running notebook
- a timeline of one's path
rather than a social media platform
or a productivity workspace.
---
# Core Philosophy
Most modern platforms emphasize results.
- finished portfolios
- resumes
- achievements
- polished outcomes
But people are more than final outputs.
Developers already have GitHub:
a visible history of commits,
iterations,
experiments,
mistakes,
and growth.
Non-developers rarely have an equivalent space.
Emprint extends the philosophy of commit history
to everyone.
A photographer,
writer,
designer,
student,
researcher,
or artist
should also be able to preserve
their process and evolution over time.
Every publication becomes a trace.
Every revision becomes part of a timeline.
Emprint is not designed for rapid consumption.
It is designed for long-term personal archives.

# Part 3 — State & time model

---

## 1. Core concept

Emprint does **not** expose Git as a version control system.

Instead, it defines a **two-layer temporal model**:

| Layer | User-facing name | Role |
|-------|------------------|------|
| **Working State** | Draft layer | Current, unpublished editing state |
| **Published narrative state** | **Imprint** layer | Linear history of publication moments |

All user actions are interpreted within these two layers. Git (commits, remotes, push) remains an **implementation detail** behind Publish, Imprint, Rollback, and Reset draft.

---

## 2. Working State (Draft layer)

### Purpose

Represents the current, **uncommitted** editing state — what the author is writing *right now* before the next publish.

### Characteristics

- Not published (not yet an Imprint entry visitors rely on)
- Not part of Imprint narrative history until published
- Ephemeral: safe to discard without rewriting history
- Includes uncommitted file changes across posts, drafts, assets, and `src/` (site) as surfaced by working-tree summary

### Operations

#### Reset draft

- Discards all uncommitted changes
- Restores the tree to the **last published state** (latest Imprint entry), or empty/bootstrap state if none exists
- Does **not** remove Imprint history

**Implementation note (planned):** maps to restoring `HEAD` to latest published commit (or `git checkout` / `git restore` of tracked files) without exposing Git vocabulary in UI.

---

## 3. Published state (Imprint layer)

### Purpose

Represents the **narrative history** of a publication — the story of “what went live,” not a developer’s branch graph.

Each **publish** event becomes one **Imprint** entry on a single timeline.

### Characteristics

- **Conceptually immutable** history (entries are not deleted from the timeline)
- Strictly **linear** ordered timeline (no branches, no merges in the user model)
- Source of truth for “what was published when” and for rollback targets
- Shown in-app as the **Imprint** sidebar surface (lane / timeline UI), **not** as `git log`

### Product rule

> Imprint is the rollback interface. Users “go back” by choosing a point on the Imprint timeline, not by checking out branches or reverting commits in Git terms.

---

## 4. Publish operation

### Definition

**Publishing** transitions the current Working State into the Imprint layer and (for GitHub Pages workspaces) triggers deployment via push.

### Effect

- Creates a new **Imprint** entry (one new point on the timeline)
- Updates **latest published state** (new baseline for Reset draft)
- Becomes visible in Imprint UI after success
- Under the hood: stage → commit → push (`git:publish` today); deploy outcome may be surfaced separately (Actions/Pages polling — see roadmap)

### User mental model

- “I publish” → a new mark on my Imprint line; my site will catch up when GitHub Actions finishes.

---

## 5. Rollback operation (Imprint-based)

### Definition

**Rollback** restores a **previous Imprint state** as the new working base.

### Behavior

1. User selects a point on the **Imprint** timeline (not a commit hash field).
2. System restores that publication snapshot into **Working State** (working tree + editor buffers policy TBD).
3. The next **Publish** continues narrative forward from that restored base (new Imprint entry when they publish again).

### Important rules

| Rule | Meaning |
|------|---------|
| History is not deleted | Older Imprint entries remain on the timeline for reference |
| Reposition, not rewrite | Rollback changes *where you are writing from*, not what was published in the past |
| Linear only | No branch picker, no merge UI, no “detached HEAD” language |

**Implementation note (planned):** likely `git checkout <imprint-commit>` or restore tree at selected SHA; UI labels use Imprint timestamps / messages only.

---

## 6. Constraints (user model)

- **No branch concept** in the user model
- **No merge concept** in the user model
- History is **strictly linear** (Imprint timeline)
- Only two exposed states:
  1. **Draft** (Working)
  2. **Imprint** (Published history)

Folders named `drafts/` refer to **post draft status** (unpublished posts), not the Working State layer — naming overlap is intentional but distinct (see AGENT_BRIEF).

---

## 7. Mental model summary

| User says | System meaning |
|-----------|----------------|
| “I write” | Working State |
| “I publish” | New Imprint entry + latest published baseline |
| “I go back” | Rollback to selected Imprint point → new Working State |
| “I reset” | Reset draft — discard uncommitted work |

Git is completely abstracted away in copy and primary flows.

---

## 8. Implementation mapping (today vs planned)

| Concept | User UI (today) | IPC / backend (today) | Gap |
|---------|-----------------|------------------------|-----|
| Working State | Dirty indicators, Publish dialog summary | `git:working-tree` | No **Reset draft** action |
| Publish | Sidebar Publish → dialog | `git:publish` | Deploy status not in Imprint |
| Imprint timeline | Imprint section (lane UI) | `git:log` | Read-only; no rollback |
| Rollback | — | — | **Planned** |
